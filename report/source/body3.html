4.2 AI Architecture

Language models are used in three single-call steps — the Extractor, the Critic and the Spec Compiler — plus an embedding model. None is an autonomous agent: each call has a fixed schema, no tools and no memory, and its output is validated and then reviewed by a person. Prompts are versioned Markdown files whose version includes a hash of their content. Ticket text is sent only inside <ticket> delimiters in a user-role message, and delimiters inside the ticket are neutralised, so a ticket cannot close its data block and append instructions.

4.2.1 Extractor and Adversarial Critic

The Extractor returns up to 30 flags in six categories: missing information, vague language, contradiction, unhandled edge case, security/compliance gap and untestable criterion. Its output is parsed with a strict zod schema, duplicates are removed and every quoted span is checked to occur verbatim in the ticket. In the deliberated arm the Critic then returns keep/prune per candidate ({{ref:fig-pipeline}}). Four rules are enforced in code: an unreviewed candidate is kept; the Critic cannot change category or quoted span; an empty refined question falls back to the original; and both passes use the same model unless the run is marked as differing.

Random-pruning control. Pruning raises precision mechanically, even at random. The evaluation therefore compares the Critic with the same number of flags removed at random, 1000 times with a fixed seed. The Critic is kept only if p < 0.05 and no reviewer gap lost its only covering flag; the report builder refuses to produce a Critic-arm report without this control.

4.2.2 Spec Compiler, Scaffolds and Traceability

For an approved ticket version, the Spec Compiler writes one Gherkin scenario per testable behaviour, using the PM’s answers as binding decisions and quoting the criterion each scenario covers, which is verified against the real text ({{ref:fig-compiler}}). The scaffold emitter is deliberately not an LLM call: it is a pure function of the scenario, emits test.fixme and a named PLACEHOLDER_* locator for every interactive step, and lists them as a checklist. Every acceptance-criteria clause and accepted scenario is embedded (1536-dimension vectors with HNSW indexes); cosine similarity gives clause coverage and pairs stale scenarios with the closest clause of a changed ticket (drift).

Cost accounting. Every model call is logged with purpose, prompt version, request, response, latency, tokens and cost. On the 11-ticket gold set, analysis cost US$0.0030 in total (gpt-4o-mini) and scenario generation US$0.0044 (gpt-5.4-mini).

Pages are React Server Components that call repositories on the server; each mutation is a server action that resolves the user and tenant first. 5.4 Multi-Tenant Isolation Testing

The isolation suite creates two tenants and calls every repository with tenant A’s id and tenant B’s object ids: B’s data stays invisible, writes to B’s flags, tickets, sessions and vectors are refused, and usage metrics count only A’s rows. All checks pass in CI and on the local database run.

CHAPTER 6
CONCLUSION

SpecFix shows that a language model can be a dependable part of a requirements workflow when the system around it is engineered carefully. The platform ingests and versions tickets, detects six kinds of ambiguity with an Extractor and Critic, resists prompt injection, lets a human resolve every flag with a full audit trail, and turns approved tickets into Gherkin scenarios and Playwright scaffolds behind further human gates. A pgvector traceability graph reports clause-level coverage and drift, on a multi-tenant schema whose isolation is tested. Every quality figure comes from a reproducible report with confidence intervals, and figures that have not been independently measured are reported as such.

CHAPTER 7
SUMMARY

7.1 Summary

SpecFix is an AI-assisted requirements-quality platform for ordinary software teams. It finds the places in a ticket where a developer would have to guess and turns each into a precise question for the product manager; a second model pass removes false alarms, a human resolves the rest, and the ticket is marked ready with a full record of what was decided. Approved criteria then become Gherkin scenarios and Playwright scaffolds, linked by a traceability graph that shows coverage and drift.

The system is a TypeScript monorepo of seven packages with seven SQL migrations, a Next.js dashboard, an operator CLI and CI. Its defining traits are safety by construction (validated output, ticket text as data), humans in control (no automatic resolution), honest measurement (versioned prompts and gold sets, confidence intervals, a random-pruning control) and tenant isolation with per-tenant cost caps. With 270 offline tests passing (313 with the database suites) and a generation baseline of 91.7% AC coverage at about US$0.0004 per ticket, the project is ready for independent validation and Jira integration.
