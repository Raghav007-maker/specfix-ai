CHAPTER 1
INTRODUCTION

1.1 Overview and Motivation

Most software teams describe what they want built as tickets: a title, a short description and a few acceptance criteria. These tickets are written quickly and are rarely complete. A criterion such as “the refund should show up quickly” leaves the developer to decide what “quickly” means, and “the customer is notified” does not say how. Each missing decision is made silently by whoever writes the code, and the later such a defect is found, the more expensive it is to fix. Typical problems are vague words, missing values or rules, contradictions, unhandled edge cases, unstated security or audit needs, and criteria that no test could pass or fail.

Specialist requirements-quality tools exist, but they target regulated industries and sit outside the everyday ticket workflow. General chat assistants can “review a ticket”, but their answers are unstructured, unmeasured and easy to manipulate with text hidden inside the ticket. SpecFix fills this gap: a ticket goes in, structured flags come out, a human resolves each one, and the ticket is marked ready for development. The approved criteria are then turned into Gherkin scenarios and Playwright test scaffolds, with a traceability graph from requirement to test.

Why This Project?

  • Every model response is schema-validated, and ticket text is treated as data, never instructions.
  • A human resolves every flag and approves every generated scenario and scaffold.
  • The Critic is tested against a random-pruning control; tenants are isolated and every model call is costed.

1.2 Objectives

Completed Objectives (60%)

  1. Ingest and version tickets, and detect ambiguity with an LLM Extractor returning typed flags in six categories.
  2. Filter false alarms with an Adversarial Critic whose safety rules are enforced in code; resist prompt injection.
  3. Provide a review dashboard to accept, edit, dismiss or reopen flags, with an audit trail and a “mark ready” step.
  4. Measure quality with blind-first labeling, precision/recall with confidence intervals and a random-pruning control.
  5. Generate Gherkin scenarios and Playwright scaffolds behind human gates, with pgvector traceability and drift detection.
  6. Isolate tenants and cap model spending per tenant; establish a generation evaluation baseline.

Pending Objectives (40%)

  • Jira Cloud integration with a single, PM-triggered write-back at sign-off.
  • A background worker (BullMQ on Redis) for analysis, compilation and embedding jobs.
  • Independent blind labeling of real tickets, an optional conversational agent, and pilot deployment.

CHAPTER 3
SOFTWARE DESIGN

3.1 System Architecture Overview

SpecFix follows a layered architecture (Figure 1.1). The presentation layer is a Next.js 15 application using React Server Components and server actions, so no public REST API is exposed. The application layer resolves the user and tenant on every request. The domain layer is a set of TypeScript packages that return data only, and the data-access layer is the only code allowed to issue SQL. The infrastructure is Supabase (PostgreSQL with pgvector, Row-Level Security and authentication), Azure OpenAI / OpenAI endpoints and GitHub Actions CI. Two decisions run through the design: work belongs to a ticket version (identified by a content hash), so artefacts become stale instead of silently attaching to changed text; and tenant isolation is enforced in the repositories, by RLS and by a dedicated test suite.

4.2 AI Architecture

Language models are used in three single-call steps — the Extractor, the Critic and the Spec Compiler — plus an embedding model. None is an autonomous agent: each call has a fixed schema, no tools and no memory, and its output is validated and then reviewed by a person. Prompts are versioned Markdown files whose version includes a hash of their content. Ticket text is sent only inside <ticket> delimiters in a user-role message, and delimiters inside the ticket are neutralised, so a ticket cannot close its data block and append instructions.

4.2.1 Extractor and Adversarial Critic

The Extractor returns up to 30 flags in six categories: missing information, vague language, contradiction, unhandled edge case, security/compliance gap and untestable criterion. Its output is parsed with a strict zod schema, duplicates are removed and every quoted span is checked to occur verbatim in the ticket. In the deliberated arm the Critic then returns keep/prune per candidate (Figure 4.1). Four rules are enforced in code: an unreviewed candidate is kept; the Critic cannot change category or quoted span; an empty refined question falls back to the original; and both passes use the same model unless the run is marked as differing.

Random-pruning control. Pruning raises precision mechanically, even at random. The evaluation therefore compares the Critic with the same number of flags removed at random, 1000 times with a fixed seed. The Critic is kept only if p < 0.05 and no reviewer gap lost its only covering flag; the report builder refuses to produce a Critic-arm report without this control.

4.2.2 Spec Compiler, Scaffolds and Traceability

For an approved ticket version, the Spec Compiler writes one Gherkin scenario per testable behaviour, using the PM’s answers as binding decisions and quoting the criterion each scenario covers, which is verified against the real text (Figure 4.2). The scaffold emitter is deliberately not an LLM call: it is a pure function of the scenario, emits test.fixme and a named PLACEHOLDER_* locator for every interactive step, and lists them as a checklist. Every acceptance-criteria clause and accepted scenario is embedded (1536-dimension vectors with HNSW indexes); cosine similarity gives clause coverage and pairs stale scenarios with the closest clause of a changed ticket (drift).

Cost accounting. Every model call is logged with purpose, prompt version, request, response, latency, tokens and cost. On the 11-ticket gold set, analysis cost US$0.0030 in total (gpt-4o-mini) and scenario generation US$0.0044 (gpt-5.4-mini).

4.3.2 Ticket Review

The ticket page shows the ticket beside its flag cards with Accept, Edit, Dismiss and Reopen, followed by the decision history and readiness timeline (Figure 4.4). “Mark ready” stays disabled while any flag is open. The isolation suite creates two tenants and calls every repository with tenant A’s id and tenant B’s object ids: B’s data stays invisible, writes to B’s flags, tickets, sessions and vectors are refused, and usage metrics count only A’s rows. All checks pass in CI and on the local database run.

CHAPTER 6
CONCLUSION

SpecFix shows that a language model can be a dependable part of a requirements workflow when the system around it is engineered carefully. The platform ingests and versions tickets, detects six kinds of ambiguity with an Extractor and Critic, resists prompt injection, lets a human resolve every flag with a full audit trail, and turns approved tickets into Gherkin scenarios and Playwright scaffolds behind further human gates. A pgvector traceability graph reports clause-level coverage and drift, on a multi-tenant schema whose isolation is tested. Every quality figure comes from a reproducible report with confidence intervals, and figures that have not been independently measured are reported as such.

CHAPTER 7
SUMMARY

7.1 Summary

SpecFix is an AI-assisted requirements-quality platform for ordinary software teams. It finds the places in a ticket where a developer would have to guess and turns each into a precise question for the product manager; a second model pass removes false alarms, a human resolves the rest, and the ticket is marked ready with a full record of what was decided. Approved criteria then become Gherkin scenarios and Playwright scaffolds, linked by a traceability graph that shows coverage and drift.

The system is a TypeScript monorepo of seven packages with seven SQL migrations, a Next.js dashboard, an operator CLI and CI. Its defining traits are safety by construction (validated output, ticket text as data), humans in control (no automatic resolution), honest measurement (versioned prompts and gold sets, confidence intervals, a random-pruning control) and tenant isolation with per-tenant cost caps. With 270 offline tests passing (313 with the database suites) and a generation baseline of 91.7% AC coverage at about US$0.0004 per ticket, the project is ready for independent validation and Jira integration.
